How tight is too tight?
An audit of 187 test files

A ruthless pass over the Case Review Platform frontend test suite: which tests pin genuine contracts, which are change-detectors that tax every edit, and where ~4,000 lines can go without losing a single defect-catching assertion.

2026-08-11 187 test files · 61,923 lines · ~2,458 cases node --test · no build step 4 parallel analysts + churn mining

The verdict in three sentences

The suite is strongly bimodal: the pure-logic half (~100 files, 20k lines) is some of the most disciplined test code you will find anywhere — project-then-compare deep-equals, regex-over-exact error messages, self-testing lint detectors — while the maintainability overhead concentrates in about 15 files and six repeating patterns: class-selector view tests, business content pinned as code, coverage-driven white-box tests, mock-client triple-coverage, stub boilerplate, and exact product copy.

The churn data proves it isn't hypothetical: 92% of source commits this year also had to touch tests, and 86% of that churn was editing existing tests — and the three highest-churn test files are precisely the ones this audit flags. Roughly 4,000 lines are deletable or consolidatable with no coverage loss (~1,500 of them pure deletions), and one one-line helper fix de-brittles every table test in the repo.

§ 1

The shape of the suite

Brittleness is not evenly distributed. Grouping the analyzed files into five territories and flagging the lines each analyst marked as overhead shows where the tax actually lives.

Two territories deserve their reputation defended. The security suite (section-access-*, permissions, configured-outcome) pins the complete role-by-section access matrix cell by cell — and that is correct: the project's own test discipline mandates exact external contracts for security and outcome code, and the declarative assertGrid helper keeps the exhaustiveness readable. The pure-logic half has already internalised every habit this report recommends: 352 assertions carry explanatory messages, error asserts use short regexes (exactly one exact-message assert in 20,443 lines), and whole-object deep-equals are projected onto named fields first.

The core distinction: change-detector vs invariant

The single most useful lens from this audit. A test that hardcodes the current contents of config breaks on every legitimate edit; a test that loops an invariant over whatever exists gets stronger with every edit. The repo contains excellent examples of both — sometimes in adjacent files.

Where the white-box tests come from

The coverage-driven tests aren't carelessness — they're an incentive playing out. The 95% line/branch/function floor is a hard commit gate, and the cheapest way to reach an awkward ?? branch is a test that names it. The project's own CLAUDE.md warns against exactly this ("do not add white-box assertions solely to cover a syntactic line"), but the floor pays out either way, and four of the resulting tests in save-queue.test.js assert nothing beyond status === 'saved'.

§ 5

What is deliberately tight — and must stay

Ruthlessness cuts both ways: several of the tightest tests in the repo are tight because the thing they pin is a real external contract, and loosening them would be the defect. Any loosening pass should treat these as off-limits.

list-cases-filter-parity.test.js

The best test file in the suite. Every scenario must agree three ways — mock engine, hand-written expected ids, and a real OData evaluator that is itself tested — with an anti-tautology guard rejecting scenarios that match everything or nothing, and recorded divergences that still fail when a new one appears. It is the reason ~500 lines of mock tests can go.

The security suite

section-access-*, permissions, configured-outcome, html. Exhaustive role-by-section matrices and fail-closed defaults, asserted through public seams with declarative helpers. The project mandates exact contracts here; the audit found nothing to loosen.

The allocation block · cora-dashboard:553–1670

Optimistic-concurrency claim protocol (etag re-read, 412 retry, capacity, coalescing, disposal) asserted via recorded client calls and state — almost zero DOM coupling. The highest-value test code in the suite.

The wire contracts

Exact-body PATCH deep-equals in http-client-writes (proves no stray column reaches a field-level PATCH), the people-picker payload pins, digest/429 throttle protocol via injected sleep, and the persisted CASE_STATUS values. Exact because the wire is exact.

render.test.js — the keyed reconciler

Eighty structural DOM assertions, all correct: "the same node was moved, not rebuilt" is the contract that keeps focus, caret and scroll alive. Structural-on-purpose, like the node-identity tab-switch test in cora-case-review-slice:4120.

The invariant suites & ratchets

verify-config / verify-dead-code / verify-build test the checker on synthetic trees then run it over whatever exists — the template §3 recommends. The 19 contract ratchets are rename-sensitive by design, and several test their own detectors so they cannot rot into no-ops.

Methodology. Four parallel analysis passes (view slices · client & protocol · config & meta · pure logic) reading ~150 of 187 test files in depth, cross-checked against source under src/ and case-types/; suite-wide pattern counts via grep; churn mined from git log since 2026-01-01 (51 src-touching commits). The ~33 smaller cora-* files were sampled by pattern rather than read fully.
