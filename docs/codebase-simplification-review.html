Architecture review / maintainability

Strip the framework back to pure authoring

The current codebase is functionally healthy, but the component authoring model asks ordinary feature work to understand Web Component lifecycle, teardown, stable node identity, and manual render loops. That is the risk to junior maintainability.

Verdict Evidence Findings Target model Migration plan Decisions
Short answer
Keep h() and signals. Hide custom-element classes.

The path is not to replace the primitives. The path is to make custom elements a framework-internal shell, so app authors write pure render functions and named state mutations.

Web Components still have value at route and integration boundaries. They should not be the default shape of every component.

Review findings

Where the complexity lives

The domain logic is mostly in good shape. The friction is in the component authoring contract and a few lifecycle-heavy shells.

P1 Lifecycle-first docs

The authoring guide teaches new components as custom element classes with connectedCallback(), replaceChildren(), and manual registration. That is the opposite of the simpler model we want junior maintainers to use.

docs/guide/component-authoring.md

P1 Case Review shell overload

CORACaseReview owns route setup, view-model creation, stable node identity, controller orchestration, event binding, compatibility shims, and rendering. Changes here require broad knowledge of ordering and lifecycle.

src/pages/cora-case-review.js

P2 Mixed render models

The old base-class render surface has been removed. Remaining shell components should continue moving private _render() methods, custom update() paths, and direct replaceChildren() calls toward plain functions.

src/lib/view.js

P2 Manual teardown leaks into app code

Document-level listeners are handled correctly in the examples reviewed, but authors still need to remember the pattern: create handler, store it, add listener, remove listener on disconnect.

src/question-bank/cora-bank-editor.js

P2 Focus preservation is duplicated

Focus restoration appears in both Question Bank state commits and question-list rendering. The behavior is important, but it should be a framework-level render concern rather than a pattern each feature area has to rediscover.

src/components/cora-question-list.js

P3 The good seam already exists

Evaluators and stores are already close to the desired model: inputs in, values out, named mutations, signal-derived state. This lets us simplify the UI shell without replacing the working domain model.

Proposed target

Function components first, custom elements at the edges

The framework can keep vanilla browser primitives while giving authors an API that feels like plain functions.

Principle: ordinary feature UI should be plain functions that return h() nodes. Use reactive(() => h(...)) only where local signals need to re-render. Custom elements stay at route and browser integration boundaries. 

export function Question(props) {
 const response = signal(props.response ?? '');

 return reactive(() =>
 h('fieldset', {},
 h('legend', {}, props.text),
 props.options.map((option) =>
 h('label', {},
 h('input', {
 type: 'radio',
 checked: response.get() === option,
 onchange: () => {
 response.set(option);
 props.onAnswer?.(option);
 },
 }),
 option
)
)
)
);
}
What authors stop writing Class declarations, constructors for default props, connectedCallback(), disconnectedCallback(), manual replaceChildren(), manual effect disposal, and document listener cleanup.
Migration slices

A low-risk path

Do not start with the hardest page. Prove the primitive on leaf components, then collapse the heavier shells.

Add reactive()

Create a small wrapper for plain function components that runs a render function in an effect, replaces the host children, and disposes automatically.

Add lifecycle helpers

Provide on(target, event, handler), afterMount(fn), and cleanup registration so document-level listeners stop being hand-rolled.

Convert simple leaf components

Start with cora-toast, cora-status-banner, cora-outcome, cora-notes, and cora-section-progress. These should become examples for new authors.

Move focus preservation into the framework

Centralize stable focus-key capture and restore around framework-managed render passes. Keep component-specific focus policy only where user workflow requires it.

Refactor medium components

Convert wording/options/show-when/question-label components once the leaf conversions establish the conventions and test pattern.

Collapse CORACaseReview

Keep a route shell, but move page rendering to renderCaseReview(vm) and event behavior to named action binders. Delete compatibility shims as tests move to public behavior.

Rewrite the authoring guide

Make plain function components the default documentation. Document defineView(), raw custom elements, and class-backed elements as advanced route or integration escape hatches only.

Recommended decisions

These are the decisions that should be made explicit before implementation work starts.

Decision Recommendation Reason
Keep h()? Yes It is small, explicit, safe by default, and already blocks accidental innerHTML.
Keep signals? Yes The model is understandable and the cleanup path is now tested. Signals are not the source of authoring complexity.
Keep Web Components? Only as shells They are useful at route and browser boundaries, but should not be the everyday authoring interface.
Default component style? Pure render function Junior maintainers can reason about props, state, and actions without needing lifecycle ordering knowledge.
First implementation area? Leaf components They give fast proof, low blast radius, and good examples for the rewritten guide.
