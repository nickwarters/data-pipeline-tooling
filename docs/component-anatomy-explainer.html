01 · The pattern

One shape: a pure view, wrapped by a thin shell

Every cora-* element in this codebase has the same skeleton. The UI is a plain function that takes props and returns h() nodes — no DOM, no lifecycle, trivially testable. A thin custom-element shell then adapts that function to the browser so routes and other components can mount it as a tag and re-render it reactively.

You only ever choose which shell. There are three doors, and the decision is mechanical:

defineView()

Leaf / base components. Little or no local state; the render is essentially a pure function of props. defineView() wraps the function in a custom element and wires reactive re-render for you. Used by cora-toast, cora-status-banner, cora-question-labels.

class X extends ShellElement

Stateful sections. Holds props as instance fields, exposes update(props), and emits cora- events back up. The dominant pattern in sections/ and collections/ — e.g. cora-notes, cora-conversation.

reactive()

Route-level pages. Not a custom element at all — a plain function returning a host <div> that re-renders from signals. Every page in src/pages/ mounts through it. See docs/guide/component-authoring.md.

The rule of thumb Write the pure function first, always. Reach for defineView() if the element is basically stateless; reach for ShellElement when it owns mutable props and emits events. The shell should stay tiny — if logic is piling up inside render(), push it back into the pure function.

02 · Worked example

A leaf component with defineView()

A base-layer badge that renders a Case Outcome. The pure OutcomeBadge() is the whole UI; the shell is four lines that give it a tag and reactive re-render.

Test the function, not the element: OutcomeBadge({ outcome: 'fail' }) returns a <span> you can assert on directly, with no custom-element registration or DOM shell in the test.

03 · Worked example

A stateful section with ShellElement

A Section that lists Remediation Actions, shows an EmptyState() when there are none, and emits a bubbling cora- event when the Reviewer adds one. Props live as instance fields; the parent calls update(props) to hand new data in.

04 · Registration

There is no central registry

A component becomes available purely as a module side effect. The last line of every shell module is a customElements.define(...) call (or the defineView() call, which defines internally). There is no register-components.js — the framework-contract test asserts a global registry never comes back.

  • Import for the side effect. Whatever mounts <cora-remediation-list> must import its module so the define runs. If nothing imports it, the tag is an inert, unregistered element that fails silently.
  • The dev warning has your back. Rendering h('cora-x', ...) without a side-effect import logs, once per tag: <cora-x> is not defined — missing a side-effect import of its module? (see src/lib/html.js). If you see that in the console, add the missing import.

05 · Lifecycle

What the shell gives you for free

ShellElement and defineView() both handle the reactive plumbing, so you rarely touch lifecycle methods yourself:

  • Reactive re-render. On connectedCallback() the shell runs your render() inside effect(renderNow). Any signal your render reads is tracked, and the view re-renders automatically when it changes. No manual subscriptions.
  • Focus & selection restore. Every managed render is wrapped by captureFocus() before and restoreFocus() after (see src/lib/view.js). Give an input a data-focus-key and the caret survives an autosave-driven repaint.
  • Cleanup on disconnect. Listeners registered through on() and work scheduled with afterMount() are torn down for you when the element leaves the DOM.
Advanced escape hatch The framework replaces all children on every render, which is correct but occasionally too coarse for a large, structurally-stable subtree. When you genuinely need custom diffing, follow the structural-signature approach in src/components/sections/cora-capture-groups.js: it computes a signature of its group/field shape and only rebuilds the DOM when that signature changes. Reach for this only after measuring — the default full re-render is the norm.

06 · Events

Talking to the parent

Components never reach up into their parents. They emit bubbling custom events and let whoever mounted them listen. The conventions are uniform:

  • Use emit(). On a ShellElement, this.emit(name, detail) dispatches a CustomEvent with { detail, bubbles: true } — the one blessed way to raise an event.
  • Name it cora-*. Event names carry the same prefix as the elements and CSS, e.g. cora-remediation-add, cora-answer-change. This keeps them from colliding with SharePoint's own DOM events.
  • Payload goes in detail. Pass a plain object — { caseId, value } — never mutate a parent's state directly.

07 · Checklist

Shipping a new component

  • Pick the layer. A leaf that composes no other cora-* element goes in src/components/base/. A domain-feature unit that wires base components together goes in sections/. A page/tab-level assembly mounted directly by a route goes in collections/.
  • Write the pure function first (Red). A failing test at the smallest public seam — the plain function returning h() nodes — before any shell exists.
  • Add the thin shell. defineView() for a leaf; class extends ShellElement for a stateful section. End the module with customElements.define(...).
  • Namespace everything cora-. The tag, the event names, and the CSS class hooks all share the prefix for SharePoint isolation.
  • Add the test file. Flat in tests/, one file per subject by filename (e.g. tests/cora-remediation-list.test.js). Run npm run test:coverage — cover the behaviour at its smallest useful public seam.
  • Obey the hard rules. No third-party runtime deps, no build step, no innerHTML for user data, and never call fetch() directly — all REST goes through the SharePointClient interface.
