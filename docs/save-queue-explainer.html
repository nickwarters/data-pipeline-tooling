Debounce

Every field edit resets a 1500ms timer. Only the final value in a burst triggers a network call — rapid typing never sends intermediate states. Each field has its own independent timer slot in state.pending.

enqueue(id, 'Answers', v1);
// type again → clearTimeout, new timer
enqueue(id, 'Answers', v2);
// 1500ms later → one PATCH, last value
🏷
ETag

Every fetch captures the row's ETag. Every PATCH sends If-Match: <etag>. If the server's row has moved on (another tab saved first), it returns 412 — triggering either a silent merge or a conflict banner.

// request
If-Match: "etag-abc"
// 200 OK → store new ETag
// 412 → run conflict resolution
◎
Status Signal

A signal() inside SaveQueue drives the save indicator. Four states: saved → saving → reconnecting on network error, or conflict when another reviewer's Answer changes can't be safely merged.

this._statusSignal.set('saving');
this._statusSignal.set('saved');
this._statusSignal.set('reconnecting');
this._statusSignal.set('conflict');

Scene 02
The Queue — Block by Block

"Queue" is a slight misnomer. state.pending is a map keyed by field name — at most one pending block per field. A second edit to the same field replaces the existing block and resets its timer; it never stacks a second one. Each field's timer runs independently, so three fields edited together produce three parallel timers and three independent PATCHes.

Watch the ETag in the CLIENT lane: every successful PATCH returns a fresh ETag, which replaces state.etag and becomes the If-Match header on the next PATCH. This is what makes concurrent edits safe — if anyone else writes between our reads, our ETag goes stale and SharePoint rejects the write with 412.
