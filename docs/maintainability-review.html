Executive summary

This is a genuinely well-engineered codebase for its constraints: 1,864 tests all green in ~13s, 31 ADRs tracing every decision, a clean 11-method SharePointClient seam that makes mock-first dev work, a tiny signal library, and a hyperscript h() helper used by 100% of components (no raw innerHTML, no createElement chains). A junior engineer can be productive here.

But measured against the stated goal — "Case Type modules are the seam… no framework changes required" (docs/PLAN.md:316-319) — the seam is half-built. Case Types can configure content (questions, outcomes, capture fields, detail fields) and visibility (which of the fixed 10 sections show), but they cannot configure structure: a new tab/section requires coordinated edits to at least 4 framework files. Meanwhile the component layer has good shared infrastructure (ShellElement, defineView) that only ~60% of components actually use — the other 40% hand-roll the same lifecycle/render/dispatch boilerplate, which is exactly the pattern juniors will copy-paste forward.

Overall grade: B Strong foundations, strong test discipline; the risks are drift traps (two case-type manifests, stale CLAUDE.md, mock/http client parity by convention only) and an unfinished convergence on the component base class.

Top 5 findings (severity-ordered)

  1. High 1. Two independent case-type manifests that silently drift — case-types/manifest.js lists 4 slugs; src/setup/resolve-eligible-case-types.js hardcodes only example-review. The other 3 case types are URL-navigable but invisible on every dashboard. No test guards cross-consistency.
  2. High 2. Case Types cannot add or rename sections/tabs — section vocabulary is hardcoded in 3 hand-maintained lists that must agree (section-access.js:37-48 SECTIONS, tab-controller.js:62-99 tab list + labels, the closed sections union type in sharepoint-client.js). Contradicts PLAN.md's "no framework changes required."
  3. Medium-High 3. Component base-class adoption is inconsistent — 21/35 extend ShellElement, 8/35 extend HTMLElement raw, 25/35 hand-roll _render(), 5 hand-roll _props() projection, reactive() has zero users. ~55-65% of a typical section-component class body is shape-duplicated boilerplate.
  4. Medium-High 4. CLAUDE.md/PLAN.md are stale — CLAUDE.md lists a deleted file (register-components.js) that a contract test explicitly forbids, omits src/pages/cora-case-review/ (13 files, 901 lines), half of src/routes/, and 9 of 13 pages. Juniors' first map of the codebase is wrong.
  5. Medium 5. Magic status strings — 'In-progress', 'Actions In Progress', 'Completed' compared as raw literals in 43 places across 17 files; one typo = silent logic failure that tests may not catch for a new call site.

1. What it costs to wire something new in

This is the core question for junior maintainers. Scorecard:

New page + route — Good (3 file touches)

Create src/pages/cora-<name>.js (a plain function component) and src/routes/<name>.js (exports register(router, context) calling router.register('#/<name>', { mount, unmount })), then add one import + one call in src/setup/register-routes.js — the single hand-maintained route manifest (9 entries today). Add 1-2 more edits if the page needs a Home tile (src/pages/home-page.js, a hardcoded chain of 7 if (capabilities.isX) sections.push(...) checks) or a nav entry (cora-app-nav.js).

Verdict: the pattern is simple and consistent; a junior can copy src/routes/team-cases.js (25 lines) and succeed. The weaknesses are (a) no scaffold/checklist doc, and (b) the Home page role-gating is imperative code rather than a data-driven list of { capability, title, links } — the latter would make "add a page for role X" a one-object change.

New Case Type — Fragile (the manifest-drift trap)

The good news: scripts/scaffold_case_type.py exists, the config schema is rich (see §3), and tests/case-type-manifest.test.js guards manifest.js. The bad news is finding #1: registration is split across two unrelated files:

  • case-types/manifest.js:16-32 — CASE_TYPE_IMPORTERS / QUESTION_BANK_IMPORTERS, 4 slugs, validated on load. Used at case-open time.
  • src/setup/resolve-eligible-case-types.js:35-52 — a second, hand-written list used for dashboard/team-cases/reports eligibility. Contains only example-review.

Consequence today: product-sale-review, stress-review, and complaints open fine via #/case/{caseType}/{id} but never appear on #/dashboard, #/team-cases, or #/reports/reviewer-team. Whether that's intentional rollout staging or a bug, nothing in the codebase says so, and no test asserts the relationship between the two lists. A junior adding case type #5 will update the manifest, see their case open correctly, ship — and file a "dashboard is broken" bug two weeks later.

Also note: 'example-review' appears as a hardcoded literal in framework code beyond fixtures — resolve-eligible-case-types.js:42, permissions.js:70, question-bank-store.js:36,179.

New section/tab on the case review page — Requires framework surgery (5+ files)

A Case Type cannot introduce a "Risk Assessment" tab. Section existence is hardcoded in three places that must agree, with no runtime assertion that they do:

  1. SECTIONS const, src/services/section-access.js:37-48 (10 names)
  2. The role→mode access MATRIX in the same file (377 lines)
  3. buildCaseReviewTabs, src/pages/cora-case-review/tab-controller.js:62-99 (9 tabs, labels, order)

Plus a node in src/pages/cora-case-review/node-registry.js and typically a new controller file under src/pages/cora-case-review/. Tab labels are also hardcoded there ('Details', 'Review', 'Issues', …), as are section headings inside components (cora-notes.js:24, cora-summary.js:34,112,135,162,257, cora-appeal.js:50, etc.) — a Case Type cannot even rename "Notes" to "Reviewer Notes" despite already having a labels config field.

New component — Silent-failure footgun

There is no registry (deliberately — a contract test at tests/framework-contract.test.js:48-54 enforces that the old global registry stays deleted). Registration is a module side effect: each file ends with customElements.define('cora-x', …), and the element only exists if someone side-effect-imports the file. Using h('cora-x', {…}) without the import fails silently — the browser renders an unknown inert element, props become no-ops, nothing throws. Nothing (lint rule, test helper, dev-mode warning) enforces the import/usage pairing. This is the single most junior-hostile failure mode in the repo because it produces no error at all.

2. Component layer: good infrastructure, incomplete adoption

The framing "everything is hand-rolled" is wrong — src/lib/view.js and src/lib/html.js are a real shared base:

  • h() hyperscript is used by all 35 component files; innerHTML is blocked except via an explicit unsafeHTML() escape hatch.
  • ShellElement provides lifecycle + effect wiring + focus/selection capture-restore around re-renders. defineView() is a declarative factory. on()/afterMount() auto-dispose listeners.

The problem is convergence. Adoption census across the 35 component files (7,757 lines):

PatternCountWhat it means
extends ShellElement21/35using the base
extends HTMLElement raw8/35bypassing it (incl. 2 files that use defineView for the default export and keep a legacy class)
Hand-rolled _render()25/35re-implementing render dispatch the base already does
Hand-rolled _props() projection5/3526 lines in the worst case just to copy fields into a prop bag
defineView(…)6/35the intended modern path
reactive(…)0/35dead API — exists, documented, never used
Bespoke *-empty empty-state markup13/35no shared EmptyState() helper
_dispatchX CustomEvent wrappers14 sites / 9 filesno emit(name, detail) on the base

Concrete duplication: the _render() normalize-and-replace three-way branch (Array.isArray → replaceChildren(...els) / single / clear) recurs in cora-outcome.js:74-91, cora-remediation-section.js:396-408, cora-appeal-review.js:308-310, cora-options-editor.js:161-165, and ~20 more — and is a re-implementation of normalizeRenderResult()/replaceHostChildren() that already exist in view.js:106-117 but are not exported.

Boilerplate share, measured: in cora-outcome.js (102 lines) ~55-60% of the file is lifecycle/render scaffolding; in cora-remediation-section.js (576 lines, largest component) the class body is ~65% projectable boilerplate (63-line constructor of typed field defaults, 26-line _props(), five near-identical _dispatchX wrappers of ~14 lines each). For a junior, the copy-paste source of truth is whichever component they open first — and 8 of them teach the wrong pattern.

Where size is earned, it's well documented: cora-capture-groups.js (397) implements structural-vs-value re-render diffing to preserve focus across autosave with explanatory comments; cora-case-table.js (327) documents at lines 251-265 why row filtering must live in a dedicated effect(). These are models of how to justify complexity.

3. Configurability: what a Case Type / page can and cannot control

Can configure (per Case Type) — genuinely rich: eligibleGroups, slaHours, attributeFailures, detailFields, sections visibility + showInSummary/allowMessagesWhen, appeal routing (raisedBy/resolvedBy), outcomeOptions/labels/defaultOutcomeId, captureGroups (typed fields: text/textarea/select/radio/person/actions), questions (via .txt-JSON bank file), computeOutcome(), listName, reviewerGroup.

Cannot configure:

  • Add a custom tab/section — sections is a closed 10-key union type (sharepoint-client.js:322-338).
  • Rename any tab or section heading — labels hardcoded (§1).
  • Dashboard columns from the Case Type — cora-case-table does accept a customColumns prop (cora-case-table.js:154, customColumns ?? defaultCaseColumns(...)) which is the right pattern, but only the page can supply it; no CaseTypeConfig field flows into it.
  • Swap in a custom section component — every section is a fixed framework-owned element.
  • Role→mode access matrix — 377 lines of framework code in section-access.js, not data in the config.

The customColumns prop is the template for the fix: default-with-override, resolved at mount time. The same pattern applied to tab labels, section headings, and (eventually) a sections map that tolerates unknown keys with a component reference would close most of the gap between PLAN.md's promise and reality — incrementally, without a rewrite.

Also note the question content lives in case-types/banks/*.txt — JSON in a .txt file for SharePoint MIME reasons (documented at load-bank.js:8-11), which a repo-wide search for .json will never find; and CLAUDE.md says Question Definitions live in a shared SharePoint list while the code loads static bank files. One of the two needs updating.

4. Drift traps (the things that bite six months from now)

  1. Manifest split (§1) — highest priority; add a consistency test at minimum.
  2. CLAUDE.md directory tree is wrong: lists deleted src/setup/register-components.js (forbidden by tests/framework-contract.test.js:48-54); omits src/pages/cora-case-review/ (13 files / 901 lines — a whole controller layer a newcomer won't expect), 4 of 9 route files, 9 of 13 pages. PLAN.md still frames Slice 1 as "immediate next work" while history shows the project deep into later slices.
  3. Mock/HTTP client parity by convention: both implement the 11-method interface as unrelated classes; only tsc --checkJs and separate unit tests hold them together. No shared contract test runs the same assertions against both. Also: a leftover console.log('MockSharePointClient.patchCase payload', …) at mock-sharepoint-client.js:93-97.
  4. Status string literals — 43 occurrences / 17 files (section-access.js ×12, case-machine.js ×5, http-sharepoint-client.js ×5, …). No case-statuses.js constants module.
  5. Inconsistent page-file naming: cora-home.js and cora-reports-index.js are 2-line re-export shims over home-page.js/reports-index-page.js, while cora-dashboard.js is the real implementation. A junior can't tell from the filename which convention a file follows.
  6. Question Bank coupling: 3,984 lines (45% of it one 1,791-line CSS file); its store is a module-level singleton defaulting activeSlug to 'example-review'; 11 files outside src/question-bank/ import from inside it — it is not the bolt-on subsystem the directory layout implies.

5. What's genuinely good (keep doing this)

  • Test discipline is real: 123 test files, 1,864 tests, 0 failures, ~13s. Contract tests that enforce architectural decisions (framework-contract.test.js) are an unusually good idea — extend the pattern (see recommendations).
  • ADR discipline: 31 numbered ADRs; every survey finding could be traced to a decision. ADR-28 (scaffolding contract) + scripts/scaffold_case_type.py show the team already thinks in terms of paved paths.
  • The SharePointClient seam (11 methods, JSDoc-typed) with ?mock=1 swap is clean and is what makes the whole dev loop work.
  • SaveQueue (267 lines): debounce, ETag/412 conflict handling, backoff, signal-backed status — a single owned primitive instead of scattered fetch logic.
  • h() everywhere, innerHTML banned by construction — the XSS rule is enforced by the helper throwing, not by review vigilance.
  • Complexity is documented where it's earned (cora-capture-groups, cora-case-table workaround comments).

6. Recommendations (prioritized, junior-effort-rated)

P1 Cheap insurance, do first (each ≤ half a day)

  1. Add a consistency test: every slug in resolve-eligible-case-types.js output must exist in CASE_TYPE_IMPORTERS, and (if the current 1-vs-4 gap is intentional) an explicit allow-list documenting which case types are dashboard-enabled. Kills finding #1.
  2. Fix CLAUDE.md's directory tree and PLAN.md's Slice-1 framing; document src/pages/cora-case-review/ and the bank .txt convention. Juniors navigate by this map.
  3. Create src/lib/case-statuses.js exporting the three status constants; mechanical find-replace across 17 files; add a lint-ish test greping for the raw literals outside that module (same trick as framework-contract.test.js).
  4. Delete the console.log in mock-sharepoint-client.js:93-97.
  5. Dev-mode unknown-element warning: after page mount (or in a test helper), walk the DOM for cora-* tags where customElements.get(tag) is undefined and console.warn. Converts the silent component-registration footgun into a visible one.

P2 Converge the component layer (1-2 weeks, incremental, one component per PR)

  1. Export normalizeRenderResult/replaceHostChildren from view.js; add emit(name, detail) and an update(props) (assign-fields-then-render) to ShellElement. This deletes the _render()/_props()/_dispatchX triplet everywhere.
  2. Migrate the 8 raw-HTMLElement components onto ShellElement/defineView (start with the 2 files that already half-migrated); delete the unused reactive() or adopt it — a dead API in the shared lib teaches juniors the docs can't be trusted.
  3. Add shared EmptyState(message) helper; replace the 13 bespoke variants.
  4. Write a short "anatomy of a component" doc (or explainer HTML, matching the existing docs/*-explainer.html series) naming the ONE blessed pattern, so copy-paste propagates the right shape.

P3 Finish the Case Type seam (design work, per-feature)

  1. Route labels from CaseTypeConfig into tab labels and section headings (default-with-override, exactly like customColumns).
  2. Add an optional dashboardColumns field to CaseTypeConfig that pages pass through to cora-case-table's existing customColumns prop.
  3. Longer term: make the section list data-driven — a single source of truth (section id → label, component tag, access rules) consumed by section-access.js, tab-controller.js, and node-registry.js, so "add a section" becomes one entry + one component instead of 5-file surgery. This is the change that would make PLAN.md's "no framework changes required" true.
  4. Add a mock/http client contract test: one suite of behavioral assertions parameterized over both implementations.

P4 Hygiene

  1. Collapse the page-shim naming split (pick cora-*.js-is-real or *-page.js-is-real, apply everywhere).
  2. Consider extracting the showWhen editing helpers that 11 outside files import from src/question-bank/ into src/lib/ so the bank editor becomes genuinely optional.
