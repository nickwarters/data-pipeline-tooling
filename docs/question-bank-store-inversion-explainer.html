The Store Inversion

How the ten components that import question-bank-store.js directly get decoupled from the bank editor's state singleton — so the store flows down as properties and changes flow up as callbacks/events, and import direction points one way only.

01 The problem today

src/question-bank/question-bank-store.js is the bank editor's mutable state singleton. Ten components — across all three component layers — import it directly and call commit() from their own event handlers. Components are supposed to be below subsystem/page state in the dependency order, so every one of these arrows points the wrong way.

Today — components reach up into the store
question-bank/question-bank-store.js mutable editor state singleton
▲ ▲ ▲ import { commit, … } — 10 components
components/collections cora-case-tabs · cora-compile-drawer
▲
components/sections question-card · remediation-editor · showwhen-editor · showwhen-group · wording-editor
▲
components/base options-editor · question-labels · showwhen-leaf

base cora-question-labels commit + label state

Why it bites: these components look like reusable cora-* primitives, but they only work when the bank editor's singleton is loaded and populated. A base component like cora-showwhen-leaf cannot be reused for any other showWhen surface, cannot be unit-tested without the store, and couples three component layers to one page's private state. It also blocks moving question-bank/ under pages/ — that would turn these edges into components → pages imports, the most inverted edge possible.

02 The rule

Imports only point down the stack. State lives with the page (or subsystem) that owns it. Anything below receives state as properties and reports changes as callbacks or CustomEvents — the same properties-down / events-up contract the rest of the framework already uses (cf. the pure-view-function pattern in the component anatomy explainer).

Target — page owns the store, data flows down
pages/question-bank (bank editor page) imports the store · owns commit()
▼ properties: bank, question, tree… · onCommit callback
components/collections assemble sections, forward props
▼ props down · events / callbacks up
components/sections wire base components, no store imports
▼ props down · events / callbacks up
components/base true leaves — lib/* imports only

03 The inversion, on real code

cora-remediation-editor is the smallest offender, so it makes the clearest example. Today it imports commit and wraps every mutation in it. After inversion it accepts an onCommit callback with exactly the same shape — the diff inside the handlers is one identifier.

Before — component imports the store
// components/sections/cora-remediation-editor.js
import { commit } from
  '../../question-bank/question-bank-store.js';

export function RemediationEditor(props) {
  const q = props.question;
  …
  h('div', {
    onclick: () =>
      commit(() => {
        q.allowFreeFormRemediation =
          !q.allowFreeFormRemediation;
      }),
  });
}
After — commit arrives as a callback
// components/sections/cora-remediation-editor.js
// no store import — component is a true leaf

/** @param {{ question: any,
      onCommit: (fn: () => void) => void, … }} props */
export function RemediationEditor(props) {
  const q = props.question;
  …
  h('div', {
    onclick: () =>
      props.onCommit(() => {
        q.allowFreeFormRemediation =
          !q.allowFreeFormRemediation;
      }),
  });
}

The shell element forwards the callback the same way it already forwards ensureActionObjects and nextActionId — the pattern is not new, it just wasn't applied to the store:

Before — shell binds the singleton
class CORARemediationEditor extends ShellElement {
  render() {
    return RemediationEditor({
      question: this.question,
      // commit is imported at module scope —
      // invisible dependency on the bank editor
    });
  }
}
After — the mounting page supplies it
// question-bank/cora-bank-editor.js (page/subsystem)
import { commit } from './question-bank-store.js';

const editor = h('cora-remediation-editor', {
  question: q,
  onCommit: commit,
});
// the ONLY module importing the store is the
// subsystem that owns it
Callback or CustomEvent? Use a plain onCommit property-callback when the mounting code already sets properties on the element (all ten cases here). Reserve CustomEvent for when an ancestor other than the mounter needs to observe the change. Either satisfies the rule; callbacks are the smaller diff and match the existing props style.

Components that read store state (e.g. cora-question-labels, cora-case-tabs) follow the same shape in reverse: the state they read becomes a property (a signal can be passed as a property value, so fine-grained reactivity is unchanged — the component calls effect() on whatever it's given instead of on the imported singleton).

04 Migration plan (one component per PR)

  1. Ratchet first. Land the import-layering contract test with the ten current edges on an explicit allowlist. The test fails if a new store import appears anywhere in components/.
  2. Red — extend the component's test to mount it with an onCommit spy (and state props where it reads the store) and assert the spy receives the mutation. The test must not import question-bank-store.js.
  3. Green — replace the store import with props, and pass commit / state down from the one place that mounts the component inside the bank editor.
  4. Refactor — delete the component's edge from the allowlist; the contract test now enforces it forever.
  5. Suggested order (smallest blast radius first): cora-remediation-editor → cora-options-editor → cora-wording-editor → cora-showwhen-leaf / -group / -editor → cora-question-labels → cora-question-card → cora-case-tabs → cora-compile-drawer (largest: also imports compile/flags/simulate — its assembly logic likely moves into the bank editor page).
  6. Then the directory question is free: question-bank/ can move under pages/ as "just another page" without creating a single components → pages import.
